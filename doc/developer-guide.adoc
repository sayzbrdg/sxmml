= 開発・改修手順

この文書は sxmml の開発・改修手順を示す。検証基準は Gauche 0.9.15 とする。最初のコマンドはリポジトリのルートで実行する。構成と変更箇所は xref:architecture.adoc[構成と設計]、個々の内部定義は xref:internal-reference/index.adoc[内部リファレンス]、要求と検証範囲は xref:verification.adoc[検証方針] を参照する。

識別子の命名や改名では、xref:internal-reference/naming-conventions.adoc[命名規約] を参照する。適用範囲、接頭辞・接尾辞、構築・変換・処理の名前の選び方を定めている。

責務、状態更新、Scheme の書き方、マクロの記述は、下記の <<コーディングルール,コーディングルール>> に従って判断する。

[[必要な環境と生成物]]
== 必要な環境と生成物

開発・検証環境は Gauche 0.9.15 と開発用ヘッダ、C コンパイラ、GNU Make、`iconv` とする。`configure` は Gauche の `gauche.configure` を使用する。`package.scm` の依存条件は Gauche 0.9.15 以上である。`Makefile.in` は `gosh`、`gauche-config`、`gauche-package`、`gauche-install` を使用する。

以下の手順には、リポジトリの Git チェックアウトが必要である。取得方法は link:../README.md#最初の変換[README] を参照する。

`./configure` は `Makefile`、`sxmml.gpd`、`VERSION` を生成する。`make` は shebang 付きの `sxlc` と、必須の C 拡張 `++sxmml_native++` 共有ライブラリを生成する。CLI の生成元は `src/`、C・ヘッダ・CiSE の生成元は `src/lib/` に置き、生成した C・オブジェクト・共有ライブラリはビルドディレクトリに置く。`make check` は `test/` 配下のテストを実行し、`tools/` があれば `tools/test-measure-optimize.scm` も実行して、`test.log` に結果を残す。設定と生成の規則は link:../configure[`configure`]、link:../Makefile.in[`Makefile.in`]、link:../package.scm[`package.scm`] を参照する。

[[隔離したコピーでの確認]]
== 隔離したコピーでの確認

次の手順は現在の `HEAD` を `/tmp` に展開し、作業ツリーに生成物を置かない。別の版を検証するときは `++source_rev++` に対象のブランチやタグを指定する。`git archive` は未コミットの編集を含まない。Gauche 0.9.15 で `./configure`、`make check`、一時ディレクトリへのインストールと後述の変換を実行できる。配置したコマンドとモジュールを `PATH`・`++GAUCHE_LOAD_PATH++`・`++GAUCHE_DYNLOAD_PATH++` で選ぶため、既存のインストールを上書きしない。

[source,console]
----
scratch_dir=$(mktemp -d /tmp/sxmml-dev.XXXXXX)
source_rev=HEAD
git archive "$source_rev" | tar -x -C "$scratch_dir"
cd "$scratch_dir"
gosh -V
./configure
make check
cat test.log
install_dir=$(mktemp -d /tmp/sxmml-dev-install.XXXXXX)
make bindir="$install_dir/bin" GAUCHE_PKGLIBDIR="$install_dir/share/sxmml" GAUCHE_PKGARCHDIR="$install_dir/lib/sxmml" install
export PATH="$install_dir/bin:$PATH"
export GAUCHE_LOAD_PATH="$install_dir/share/sxmml${GAUCHE_LOAD_PATH:+:$GAUCHE_LOAD_PATH}"
export GAUCHE_DYNLOAD_PATH="$install_dir/lib/sxmml${GAUCHE_DYNLOAD_PATH:+:$GAUCHE_DYNLOAD_PATH}"
----

`make check` の成功時は、`test.log` に各検査が `ok` と表示され、各ファイルの末尾が `passed.` となる。`test/` 配下の `test-<モジュール名>.scm` は、そのモジュールを主な対象とする検査をまとめる。PMD 系は `test-pmd.scm`（pmd-source）・`test-pmd-binary.scm`（pmd-binary）、FMP7 系は `test-fmp7.scm`・`test-fmp7-source.scm`、NSD.Lib 系は `test-nsdlib.scm`・`test-nsdlib-source.scm` に分かれる。binding 検査だけのモジュール（`sxmml`）にも専用ファイル `test-sxmml.scm` を置く。

`test/test-sxlc.scm` は CLI の引数・モード・出力先・診断・終了値・後処理などを検査する。`test/test-integration.scm` は、sxmml 全体として読み込み・生成・出力等の失敗時に既存ファイルを保持する結合試験をまとめる。`test/test-helpers.scm` は、CLI を使うテストが指定した `sxlc` を使い、その失敗を検出することを確認する。`tools/` がある場合は計測ツールの検査（`tools/test-measure-optimize.scm`）も実行する。

配置先と試験範囲は別である。モジュール別のファイルにも、ソース読み込み・最適化・バックエンドを通して結果を観測する試験や、CLI 経由の試験が含まれる。各ファイルの保証範囲と制約は xref:verification.adoc[検証方針] を参照する。

同じコピー内で PMD 生成を確認するには、次を続けて実行する。出力ファイルは `melody-and-rest.sxl` と同じディレクトリにできる。

[source,console]
----
printf '%s\n' '(mml G "c8r8")' > melody-and-rest.sxl
sxlc -m pmd -O 0 melody-and-rest.sxl
cat melody-and-rest.mml
----

この例では `Processing Mode: pmd-source`、`Optimize level: 0`、`Track G: total: 24` と表示し、生成物に `G l%12o4cr` を含む。日本語メタデータの符号化を確かめる手順は xref:release-guide.adoc#符号化と生成物の確認[配布・互換性] に示す。エラー・境界値の再現コマンドは xref:behavior-spec.adoc#失敗条件と境界値[外部動作仕様] を参照する。

[[テストの単独実行]]
== テストの単独実行

`test/` 配下のテストを単独で実行する際は、環境変数 `++SXMML_SXLC++` にテストで使用する `sxlc` を設定する。以下は、`./configure` と `make` でビルドした後に、リポジトリのルートで実行する例である。

[source,sh]
----
GAUCHE_DYNLOAD_PATH="$PWD/build${GAUCHE_DYNLOAD_PATH:+:$GAUCHE_DYNLOAD_PATH}" SXMML_SXLC=./build/sxlc gosh -I. test/test-sxlc.scm
----

[[文書生成の現状]]
== 文書生成の現状

man ページは `make man` で `doc/sxlc.1.md` から Pandoc により生成し、`make install` で配置する。Pandoc がない場合は man ページの生成・配置だけを省く。手順は xref:release-guide.adoc#man-ページの生成と配置[配布・互換性] に示す。`Makefile.in` には man ページ以外の文書を生成するターゲットはない。

AsciiDoc の資料は、Docker の Asciidoctor（またはローカルの `asciidoctor`）で HTML 表示を確認できる。リポジトリのルートから次を実行する。`-R doc` により元のディレクトリ構造を出力先にも保ち、文書間の相対リンクを使えるようにする。出力は新規の一時ディレクトリへ置き、ソースは読み取り専用でコンテナーに渡す。

[source,console]
----
render_dir=$(mktemp -d /tmp/sxmml-internal-reference.XXXXXX)
docker run --rm -v "$PWD:/work:ro" -v "$render_dir:/out" -w /work \
  asciidoctor/docker-asciidoctor:latest asciidoctor -R doc -D /out \
  doc/*.adoc doc/internal-reference/*.adoc
----

[[pmd-source-の仕様根拠と値の検査]]
== pmd-source の仕様根拠と値の検査

pmd-source の対応済み命令・定義は、公開されている link:https://github.com/d2lmirrors/pmd/blob/master/mc/PMDMML.MAN[PMDMML.MAN] を仕様の根拠として検査する。FM・SSG・PCM の区分で範囲を分け、細かな種別差は最も広い範囲に合わせる。対象音源の列挙だけで使用を禁止せず、効果を再現しない。曖昧な記載から推測で制限を加えず、MC.EXE による実測はこの検査方針の前提にしない。MC.EXE の受理やドライバでの演奏を包括的に保証するものではない。

検査は生成する値の出力箇所に置く。最適化で消えた命令や出力されない音色を追加走査しない。各範囲は xref:behavior-spec.adoc#pmd-source-の出力値の検査[外部動作仕様]、内部手続きは xref:internal-reference/pmd-source.adoc[PMD ソース内部リファレンス] を参照する。pmd-binary のバイナリ形式の確認は、MC.EXE の生成物の差分を根拠とする別方針に従う。

[[変更種別ごとの調査と確認]]
== 変更種別ごとの調査と確認

トラックとパートの対応情報の本体は、環境の名前→コンテキストの表とコンテキストの `part` スロットとする。常設の逆引き表は持たず、登録時に自身以外のパート所有者を確認する。新規登録・同名再定義は新しいコンテキストを生成し、名前変更（`sxmml-track-rename!`）は既存コンテキストを保持する。検査は各手続きの変更前に行い、複数登録全体の巻戻しは行わない。

コンテキストや登録表を直接編集する利用者は、対応関係を維持する責務も持つ。一対一対応を崩した場合の候補選択と生成物の再現性は保証しない。

`sxmml-track-list` の戻り値の順序は保証しない。順序に依存する処理は利用側で並べ替える。バックエンドは出力形式に従う決まった処理順を定め、ハッシュ表の反復順や `sxmml-track-list` の列挙順へ依存せず、要求仕様 Q-03 の生成物の再現性を満たす。

変更前に xref:architecture.adoc#代表的な変更時の調査先[構成と設計の対応表] から関係モジュールを特定する。`make check` に加え、変更した振る舞いに対応する xref:verification.adoc#要求と検証の対応[検証方針] の入力・観測点を確認する。

[cols="1,2,2",options="header"]
|===
|変更種別 |調査の入口 |確認する結果
|MML 構文・音長 |`sxmml/mml.scm`、`sxmml/command.scm`、`sxmml/classes.scm` |通常・リズム双方の解析結果、tick、生成行、失敗条件
|マクロ・オブジェクト加工 |`sxmml/compiler.scm`、`sxmml/processor.scm`、`sxmml/environment.scm` |反復・echo・delay の登録列と文脈、各バックエンドの出力
|最適化 |`sxmml/optimizer.scm`、`sxmml/repeat-tree.scm`、`sxmml/backend/pmd.scm` |水準別のオブジェクト数と列、生成物、xref:verification.adoc#q-01-音楽的な意味の保持[Q-01 の検証方法] で比較できる範囲。サイズ・オブジェクト数・時間は <<最適化の水準の比較,最適化の水準の比較>> で測る

|配布 |`configure`、`package.scm`、`Makefile.in`、`tools/distcheck.sh` |生成物、テストログ、ステージングの配置、man ページの有無。`tools/distcheck.sh` で xref:release-guide.adoc#配布前の確認[配布前の確認] を行う
|===

[[最適化の水準の比較]]
== 最適化の水準の比較

`tools/measure-optimize.scm` は、1 つのソースを最適化の水準ごとに変換し、生成物のバイト数、全トラックのオブジェクト数の合計、時間を表にする。`-O 3`・`-O 4` の圧縮の設定（展開の上限 E と窓幅 W）を変えたときの効果と時間を比べるのに使う。リポジトリのルートで次のように実行する。

[source,console]
----
GAUCHE_DYNLOAD_PATH="$PWD/build${GAUCHE_DYNLOAD_PATH:+:$GAUCHE_DYNLOAD_PATH}" gosh -I. tools/measure-optimize.scm [-m モード] ソース.sxl [設定 ...]
----

モードの既定は `pmd` で、`pmd-binary` なども指定できる。設定は `O2`・`O3`・`O4` のいずれかで、`:E=数`・`:W=数` を付けると圧縮の設定を変えられる（例: `O4:E=128:W=256`）。既定は `sxlc` の `-O 3`・`-O 4` と同じで、E が 256、W が `O3` で 256、`O4` で 1024 である。設定を省略すると `O2`・`O3`・`O4` を測る。

[source,console]
----
$ printf '%s\n' '(mml A "[aaaaaaaa]2 cdecdecd")' > repeat.sxl
$ GAUCHE_DYNLOAD_PATH="$PWD/build${GAUCHE_DYNLOAD_PATH:+:$GAUCHE_DYNLOAD_PATH}" gosh -I. tools/measure-optimize.scm repeat.sxl
config           bytes      vs O2    objects  generate   total
O2                      110 100.0%         18       0.02       0.74
O3                      106 96.4%          13       0.01       0.72
O4                      104 94.5%          11       0.02       0.75
----

列は、設定、生成物のバイト数、`O2` との比（`O2` を先に測ったときだけ）、オブジェクト数の合計、生成の時間（秒）、親側で測る子プロセスの起動から終了までの時間（秒）である。時間列の値は実行環境によって変わる。設定ごとに別のプロセスで変換し、生成物は一時ディレクトリに置いて測り終えたら消す。変換に失敗した設定は `failed (exit status N)` と表示する。圧縮の設定は `sxmml.optimizer` の内部変数を書き換えて変えるため、その名前を変えたときはこのツールも合わせて修正する。`make check` の `tools/test-measure-optimize.scm` が合成入力で動作を確かめる。

親側の `driver` は全設定を実行前に解析し、指定順の走査・`O2` 基準値・表示を担当する。局所手続き `run-config` は、1 設定分の一時領域の確保、子プロセスの起動、結果回収、後始末を担当し、終了値・親側の経過時間・結果行の 3 値を返す。表示する `total` は、一時領域と結果パスの準備後、`run-process` の前から子の終了後までの時間であり、結果ファイルの読み取りと後始末は含まない（結果行に保持している子側の `total` とは区別する）。

[[コーディングルール]]
== コーディングルール

本節は、新規実装と改修時に適用する規約と判断基準をまとめる。現行動作の説明は xref:behavior-spec.adoc[外部動作仕様]・xref:sxmml-reference-manual.adoc[MML 記述者向けリファレンス] を参照する。

評価回数・実行順・入力の更新可否などは、各処理が守る契約とする。走査や構築に使う手続きの選択は、処理の目的・読みやすさ・構築費用に応じた指針とする。

[[責務と状態更新]]
=== 責務と状態更新

* 公開入口とモジュール間の境界では、入力の前提・戻り値・更新対象を明確にする。局所ヘルパーの説明は必要に応じて行い、すべてに定型的な仕様コメントを要求しない。
* 共通処理には操作する文脈や設定を明示的に渡す。パラメータは利用者向けの入口や PEG との受け渡しなど、必要な境界で使う。
* 共有する入力、登録対象、作業領域を区別する。入力を変更しない変換では、変更する部分を新しく構築し、変更しない部分の共有を認める。
* 整列化・最適化は入力 IR を変更しない。登録中の IR、出力用の IR 列、最適化結果の間でオブジェクトを共有でき、完全な複製やインスタンス同一性は保証しない。共有 IR を再編集する処理は、変更が及ぶ範囲を複製する。バックエンドも同じ規約に従う。
* 再生成する IR は、原型のクラスと変更対象以外のインスタンススロットの値・未束縛状態を保持する。浅いコピーのため値自体は共有できる。合成の原型に選ばれなかった IR や、削除・上書きされた IR の付加情報の保存は保証しない。
* クラスへの所属に基づいて処理を選ぶときは `is-a?`、複合した型制約の検査には `of-type?` を使う。状態の鍵は命令の意味を表すシンボルとし、クラスオブジェクトと区別する。同一クラスの比較は `class-of` の結果を `equal?` で比較する。
* 具体的な IR クラスの派生は、対応する既知の命令の最適化規則に従う。既知の特殊化は親より先に扱う。独自の効果に親の規則を適用できない場合は共通基底から定義する。
* 作業用バッファの更新など、責務に応じた破壊的更新を認める。局所的な計算については、次節の参照透過性を基本とする。
* 検査は担当する層で行う。共通登録での検査に加え、手作り IR を受け取れるバックエンドは出力上の要求を検査する。記述の整理に伴って検査責務や診断の優先順位を暗黙に変更しない。

[[schemeの書き方]]
=== Scheme の書き方

モジュール内で完結し、引数と戻り値で自然に表現できる処理は、参照透過に書くことを基本とする。破壊的更新や暗黙の状態への依存は、その処理の責務や性能上の必要性に応じて選ぶ。

外部に漏れない局所状態でも、自然に引数で引き回せるならその形を優先する。オブジェクトで情報をまとめることと、その内容を更新する必要があることは分けて判断する。

例外の送出は必要な制御の副作用として扱う。入力検査を担当する手続きは直接エラーを送出できるが、判定のために不要な可変状態を導入しない。判定結果を使ってエラーを送出する形を基本とし、判定を別の手続きに切り出すかは再利用と読みやすさに応じて判断する。

その処理に状態変更が必要かを判断してから、目的に合う語彙を選ぶ。

[cols="1,1",options="header"]
|===
|処理の目的 |基本となる書き方
|各要素から結果の列を作る |`map`
|値の集約や構造の構築 |`fold`
|存在・全件の判定 |`any`・`every`
|各要素に副作用を実行する |`for-each`
|複数の進行状態を引き回す |名前付き `let` による末尾再帰
|===

名前付き `let` による末尾再帰は、状態を引き回す処理の自然な書き方として使う。標準手続きで目的を直接表せる単純な走査と、進行状態を持つ再帰を区別する。

たとえば、`define-track` の複数トラック形式では、キー・値列を組にしてからキー位置の `:part` の存在を判定する（値の欠落検査は `make` 側の責務とする）。

[source,scheme]
----
(when (any (^[kv] (eq? (car kv) :part))
           (slices param 2))
  (sxmml-form-error
    form
    "invalid define-track form: :part requires a single track"))
----

走査順、式の評価順、結果列の順序を区別する。`fold` で `cons` を積む場合も、得られる列の順序が後続の処理の契約を満たすか確認する。中間リストの構築費用も判断に含め、手続きの抽出は再利用と読みやすさに応じて行う。

中間表現は、責務の境界、保存・再利用、読みやすさ、構築費用で判断する。一度だけ消費することを理由に一律に取り除かない。削除によって責務の混在や再計算が増えるなら、列として保持してよい。

`append` は先頭側のコピー、`append!` も末尾までの走査を伴う。単なる連結が必要というだけで選ばず、後続列を受けて構築できるか、所有する逆順列を後続列の前へ反転できるかを考える。共有する入力を破壊的につながない。ジェネレータを渡す方式への変更は、消費回数や例外の発生時点等のインタフェース変更として扱う。

[[マクロの共通規約]]
=== マクロの共通規約

* 構文上の名前・枠と、評価する式の位置を区別する。
* 書式は展開時に検査し、値の意味や登録状態は実行時に扱う。
* マクロは書式検査と手続き呼び出しへの展開を担い、実際の処理は手続きに置く。重複する展開処理は、読みやすさを保てる単位で共有する。
* 展開結果の構造は原則 `quasirename` で示し、式列の組立ては通常の Scheme として書く。展開結果で使う実装側の識別子の衛生性を保つ。
* 式の評価時点・回数と、複数対象の実行順を、それぞれのマクロの契約として守る。利用者の式が持つ副作用も、その契約に従って保持する。
* 名前の正規化とエラー通知は、以下の規約に従う。

たとえば、次の本文は 1 度だけ評価し、得た MML 文字列を `A`・`B` で共有する。

[source,scheme]
----
(mml (A B) (next-phrase))
----

`next-phrase` は 1 度評価し、その後各トラックの解析文脈で指定順にコンパイル・登録する。`mml-delay` の 3 値と本文も各 1 度の評価・共有とし、`let` で束縛する。共有式同士の固定評価順は保証しない。生成した IR はトラックごとに作り、共有しない。

`mml`・`rhythm`・`define-track` の複数トラック形式は指定順に実行する。`define-track` のパラメータ式はトラックごとに評価する。`mml-repeat` は回数式を終了直前に 1 度評価して対象トラックで共有し、反復命令は `sxmml.command` で IR を直接生成して文脈の集計と使用規則をパーサーと共用する。`mml`・`rhythm` の共通展開は `compiler.scm` 内の非公開手続きへまとめ、固有の加工を持つ `mml-delay` の展開は `processor.scm` 内に置く。

[[マクロの名前種類キー]]
=== マクロの名前・種類・キー

展開時の単語は、利用者マクロ由来の識別子にも対応するため `identifier?` で検査する。MML から参照する音色・LFO・エンベロープの定義名は `sxmml.form` の `sxmml-form-name\->symbol` に集約し、シンボル・数値を正規化して空白・波括弧・空の名前を拒否する。

種類とトラック名は検査後にそのままクオートし、Gauche にシンボル化させる。メタデータキーは `identifier\->symbol` で元の名前を得て小文字化する。名前のために任意の入力を `x\->string` へ渡さず、値の式を含むフォーム全体に `unwrap-syntax` を適用しない。診断用に不正な項目や名前を表示するときだけ、その項目の識別子を取り除く。

[[既知の入力エラーの通知]]
=== 既知の入力エラーの通知

明示的な入力検査は、違反した規則に応じて `error`・`errorf` のコンディション型指定で送出する。MML 文字列の規則は `<sxmml-mml-syntax-error>`、独自マクロの構文は `<sxmml-form-syntax-error>`、登録・出力値は `<sxmml-value-error>`、未定義参照は `<sxmml-reference-error>` として区別する。IR や最適化の内部整合性検査は既知の入力エラーとは別に扱う。

位置は本文へ埋め込まず、既存の境界で `sxmml-error-with-context` により合成する。判定には複合コンディション対応の述語を使う。未知の Gauche エラーを各手続きで `guard` して入力エラーへ変換しない。CLI は既知の入力エラーだけを `sxlc: error: …` の形で標準エラーへ表示し、Gauche の例外見出しやスタックトレースを付けない。未知の例外は Gauche の標準報告を使う。診断文は項目・指定値・必要な条件を示し、位置とトラックは CLI が文脈から組み立てる。

[[障害調査の入口]]
== 障害調査の入口

モードは `<sxmml-mode>` として共有表へ登録し、`sxmml-mode-select!` で選択する。楽曲環境は選択したモード情報だけを保持し、出力手続きと拡張子はモード情報から参照する。

* **モード未指定で止まる場合**: CLI の `-m` またはソースの `sxmml-mode` と、`sxmml-mode-get` が返すモード情報を確認する。
* **構文エラー**: 入力付近とトラック名が表示されるため、`sxmml/mml.scm`・`sxmml/command.scm`・`sxmml/compiler.scm` を辿る。
* **音色・LFO・エンベロープ未定義や値範囲エラー**: 生成段階で起き得るため、対象バックエンドのモジュール（`sxmml/backend/` 配下）を確認する。
* **出力先や最適化水準の食い違い**: `sxlc` が `-o`、ソースの `default-output-path`、入力名とモード拡張子による既定値の順で出力先を決め、整数の最適化要求・入力元とともに出力環境へ渡す流れ（`src/sxlc.in`・`sxmml/output.scm`）を確認する。

エラーの条件と境界値は xref:behavior-spec.adoc#失敗条件と境界値[外部動作仕様]、既知の課題・再現条件は link:https://github.com/sayzbrdg/sxmml/issues[既知の課題（GitHub の issue）] を参照する。
