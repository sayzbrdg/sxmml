= sxmml 要求仕様

この文書は sxmml の製品要求と実装状態を示す。動作環境は Gauche 0.9.15 である。製品の目的・利用者・境界は xref:product-overview.adoc[製品概要] を参照する。

[[製品要求]]
== 製品要求

[cols="1,2,2,3",options="header"]
|===
|ID |要求 |判定の観点 |実装箇所
|R-01 |Scheme を使い、古い MML の制約に妨げられず柔軟に MML を記述できる |現行実装で再現できる記述例と制約 |link:../sxmml/compiler.scm[`sxmml/compiler.scm`] の `mml`・`rhythm`、link:../src/sxlc.in[`sxlc`] のソース読み込み
|R-02 |Scheme から MML オブジェクトを操作できる |現行実装で利用者が操作できる対象・方法・結果 |link:../sxmml/classes.scm[`sxmml/classes.scm`] の MML クラス、link:../sxmml/processor.scm[`sxmml/processor.scm`] の変換マクロ
|R-03 |既存ドライバー向け MML で手作業だった最適化を自動化できる |現行実装が行う最適化の種類とコンパイル後のオブジェクト数の削減 |link:../sxmml/optimizer.scm[`sxmml/optimizer.scm`] の個別処理・標準組合せ、link:../src/sxlc.in[`sxlc`] の `-O`
|R-04 |sxmml が変換結果の生成物を作る |現行実装の入力・出力形式と生成結果 |link:../sxmml/backend/pmd-source.scm[`pmd-source.scm`]・link:../sxmml/backend/pmd-binary.scm[`pmd-binary.scm`]・link:../sxmml/backend/fmp7-source.scm[`fmp7-source.scm`]・link:../sxmml/backend/nsdlib-source.scm[`nsdlib-source.scm`]
|===

R-04 は生成物を MML に限定しない。現在の出力は PMD 向け MML（CP932 `.mml`）、PMD バイナリ（`.m`）、FMP7 向け MML（CP932 `.mwi`）、および NSD.Lib 向け MML（UTF-8 `.mml`）である。PMD バイナリは MC.EXE の出力との同一性を保証しない。生成先は `sxlc` の `-o`、ソースの `sxmml-default-output-path-set!` による既定値、入力名とモードの既定拡張子による値の順に選び、生成先・CLI 表示・`-c` に渡すファイル名が一致することを要求する。相対パスはカレントディレクトリを基準とし、`filename` メタデータは出力先の決定には使わない。

`-c` のコマンド文字列は指定者が引用・エスケープする。sxmml がその後ろに追加する生成ファイル名は、`-w` の有無にかかわらず 1 つの引数として後処理へ渡すことを要求する。空白や `;` を含む生成名も 1 引数で渡る。

R-01・R-02 については、Scheme 式で作った MML 文字列リストを `mml`・`rhythm` に渡せる。MML オブジェクトのスロットを直接変更することも可能だが、関連する文脈値は自動で更新されない場合がある。スロットを直接編集する場合は、関連する文脈値も利用者が更新する必要がある。

`rhythm`・`mml-repeat`・`mml-echo`・`mml-delay` の基本形を利用できる。`mml-echo` は単一トラックを受け付け、`mml-repeat` の 3 本文形式では第 3 節の本文を反復後に置き、`mml-delay` は音符の後の休符を対象とする。

MML ソース内では `define-track`・`rename-track`・`sxmml-resolution`・`define-metadata`・`define-lfo`・`define-envelope`・`define-opn-voice`・`define-opm-voice`・`define-pcm-voice`・`define-waveform`・`sxmml-mode` を利用できる。`define-metadata` の値は式として評価する。モードは登録済みの正式名・別名から選び、`sxlc -l` で一覧を確認できる。CLI の `-m` とソースの `sxmml-mode` が重なった場合は CLI 側を優先する。公開手続き `sxmml-mode-select!` による明示的な切り替えもできる。定義値の生成物への反映は xref:behavior-spec.adoc[外部動作仕様] を参照する。

LFO・エンベロープの値は、Scheme 式で組み立てたプロパーリスト（空リストを含む）を指定できる。種類への対応、要素数、個々の値の制約はバックエンドが出力時に検査する。旧枠形式も非推奨の警告付きで受理し、曖昧な一般の手続き呼び出しには登録手続き（`sxmml-lfo-set!`・`sxmml-envelope-set!`）を用いる。

R-03 の最適化は、コンパイル後の平坦な IR リストのオブジェクト数を減らす処理である。バックエンドが出力する最終文字列の長さは評価基準に含めない。代表的な処理は、重複した音量指定の削減、連続休符の結合、および局所反復木による反復圧縮である。

[[優先順位]]
== 優先順位

R-01 の柔軟な MML 記述と R-02 の MML オブジェクト操作を、R-03 の最適化自動化より優先する。R-01 と R-02 の間の順位、および R-04 との順位は未定である。R-03 も製品の対象に含む。

[[境界品質互換性]]
== 境界・品質・互換性

* 製品の範囲は xref:product-overview.adoc#責任範囲[製品概要] に定める。
* 動作環境は Gauche 0.9.15 である。言語・ライブラリの仕様は link:https://practical-scheme.net/vault/Gauche-0.9.15-refe.pdf[Gauche 0.9.15 Users' Reference] に従う。
* **Q-01**: 最適化前後で、sxmml がコンパイルした後のオブジェクトリストを解釈した結果の意味が等しいことを要求する。バックエンドの先にいるドライバーの発音は判定対象に含めない。表記やオブジェクト列が異なっても、解釈した意味が等しければ保持されている。全入力での成立は未実証である。通常の最適化を避けるには `-O 0` を指定する。対応状況は link:https://github.com/sayzbrdg/sxmml/issues/8[issue #8] を参照する。
* Q-01 の比較では、休符の連結、音量の相対指定と絶対指定、音長の既定値と明示指定など、異なる表記で等しい意味になる場合を扱う。比較方法は xref:verification.adoc#q-01-音楽的な意味の保持[検証方針] に定める。
* Q-01 の初期比較器は、単一トラックの通常音符・休符・音量・有限反復を解釈し、音符ごとの観測と列終了時の総 tick・音量への効果を比較する。`make check` で比較器の自己検証と標準組合せ 4 条件の意味保持を確認する。`L` は部分判定とし、未対応 IR や実行上限により結論を得られない場合は未判定とする。
* **Q-02**: ソースの読み込み、生成、出力先への書き込みのいずれかで変換が失敗し、`sxlc` がエラーとして終了する場合は、0 以外の終了値で終了し、出力先の既存ファイルを変更せず、途中までの生成物や一時ファイルを残さないことを要求する。対象は `sxlc` が出力先に書くファイルであり、ソース中の Scheme 式が自ら書き込むファイルや、強制終了など `sxlc` が処理できない中断は含めない。出力先が入力ファイルと同じ場合は変換を行わず、ソースを変更しない。`-c` の後処理の失敗は変換の失敗に含めず、生成物を残して別の終了値で示す。終了値の体系と個々の失敗条件は xref:behavior-spec.adoc#失敗条件と境界値[外部動作仕様] に示す。
* **Q-03**: 同じ入力ファイル（ファイル名を含む）、モード、最適化水準、sxmml と Gauche の版で変換した生成物が、バイト単位で一致することを要求する。生成物の意味の同一性はバックエンドの出力形式ごとに異なるため、全てのバックエンドに共通する条件として、意味ではなくバイト単位の一致を求める。バックエンドは、ハッシュ表の反復順など実行ごとに変わり得る順序に依存して出力してはならない。利用者がコンテキストや登録表を直接編集してトラックとパートの一対一対応を崩した場合は、候補選択とそれに依存する生成物の再現性を保証しない。
